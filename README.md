
# Trip Service

Сервис для управления поездками (TripGo). Реализован в рамках курса «Разработка микросервисов на Go».

## Требования

- Go 1.26+
- Docker Desktop (с WSL2 Integration)
- `tripgoctl` (утилита курса)
- `golangci-lint` (для проверки кода)
- `gcc` (для запуска тестов с флагом `-race`)

## Быстрый старт

1. **Поднимите окружение:**
   ```bash
   tripgoctl environment start
   tripgoctl connect
   ```
   *(Убедитесь, что в файле `.env` есть все необходимые переменные, включая `OTEL_*`.)*

2. **Накатите миграции:**
   ```bash
   make migrate
   ```

3. **Запустите сервис:**
   ```bash
   make run
   ```

Сервис будет доступен по адресу `http://localhost:8080`.

## Архитектура

Сервис разделён на слои с однонаправленными зависимостями (зависимости направлены внутрь):

1. **`internal/domain/trip`** — доменные модели и правила (статусы, валидация, переходы состояний). Не импортирует ничего, кроме стандартной библиотеки.
2. **`internal/model`** — плоские структуры данных для передачи между слоями. Не знают про бизнес-логику.
3. **`internal/usecase/trip/...`** — бизнес-сценарии (`create`, `get`, `finish`). Знают про домен и интерфейсы репозитория/транзакций.
4. **`internal/repository/trip`** — работа с PostgreSQL (SQL-запросы).
5. **`internal/http/trip/...`** — тонкие HTTP-хендлеры. Не знают про БД, вызывают usecase.
6. **`internal/container`** — единственное место, где собираются все зависимости (composition root).
7. **`internal/infra`** — телеметрия (OTel, логи) и работа с пулом БД.

Интерфейсы зависимостей объявлены на стороне потребителя (в `contract.go` юзкейсов и хендлеров), моки генерируются через `mockgen`.

Интерфейсы зависимостей (репозиторий, менеджер транзакций, метрики, логгер) объявлены в `contract.go` на стороне потребителя (в пакетах `usecase`), так как именно юзкейс формулирует, что ему нужно. Это позволяет легко подменять реализации (например, для тестов) и избегать циклических зависимостей. Сборка всех реализаций происходит в `internal/container`.

## Тесты

Для запуска всех тестов используется команда:

```bash
make test
```

**Важно:** В соответствии с `conventions.md` (п. 6), тесты запускаются с флагом `-race`. Для работы детектора гонок требуется `CGO_ENABLED=1` и установленный компилятор `gcc`.

Для запуска тестов с флагом -race требуется CGO_ENABLED=1 и установленный компилятор gcc. В стандартном окружении (CI, Ubuntu) достаточно выполнить:

```bash
sudo apt install gcc
go env -w CGO_ENABLED=1
make test
```

**Интеграционные тесты** (требуют запущенного PostgreSQL и применённых миграций):

```bash
make test-integration
```

### Покрытие

- `internal/usecase/...` — 100%
- `internal/domain/...` — 92.9%

Проверить, что домен не импортирует инфраструктуру, можно командой:

```bash
go list -deps ./internal/domain/... | grep -E 'jackc/pgx|go-chi|net/http' && echo "НАРУШЕНИЕ"
```

Команда должна ничего не вывести.

## Observability

Сервис инструментирован через OpenTelemetry SDK. Метрики и трейсы отправляются по OTLP в OTel Collector.

- **Трейсы:** Корневой спан на HTTP-запрос, вложенные спаны на каждый SQL-запрос (через `otelpgx`). Видны в Jaeger.
- **Метрики:**
  - HTTP: `http.server.request.duration`, `http.server.active_requests`.
  - Бизнес: `tripgo.trips.created`, `tripgo.trips.completed`.
  - БД: `db.client.operation.duration`.
  - Видны в Prometheus и Grafana.
- **Логи:** Структурные JSON-логи через `slog`. Каждая запись содержит `trace_id` и `span_id` (если запись сделана внутри спана). Бизнес-события (создание/завершение поездки) логируются отдельно.

Бизнес-события (`trip created`, `trip completed`) логируются внутри юзкейсов, а не в HTTP-middleware. Это позволяет сохранить контекст (например, `trip_id`) и не засорять логи транспортного слоя.

В метриках HTTP и трейcах атрибут `http.route` содержит шаблон маршрута (например, `/api/v1/trips/{tripId}`), а не полный URL. Это нужно, чтобы метрика не создавала новую временную серию для каждой поездки и корректно агрегировалась.

Middleware подключены в строго фиксированном порядке: `Recover` → `Tracing` → `Logging` → `Metrics` → роутер. `Recover` перехватывает панику, возвращает `500` и логирует стектрейс, не роняя процесс.

## Принятые решения

1. **Слои и интерфейсы:** Интерфейсы объявлены на стороне потребителя (usecase, хендлеры), чтобы избежать циклических зависимостей и упростить мокирование. Сборка всех зависимостей вынесена в `container`.
2. **Домен:** Домен не знает про инфраструктуру. Валидация и переходы состояний (`Finish`) описаны в домене.
3. **Ошибки:** Доменные ошибки объявлены в домене. Единый маппинг «доменная ошибка → HTTP-код» находится в `internal/http/domainerror`.
4. **Транзакции:** `TxManager` перенесён в `infra/postgres/transaction`. Usecase оборачивает вызовы репозитория в транзакцию, обеспечивая атомарность (например, создание поездки и записи в историю).
5. **Телеметрия:** Метрики `db.client.operation.duration` и бизнес-логи добавлены вручную, так как автоматические метрики `otelhttp` не соответствовали требованиям по лейблам и не умели определять маршруты `chi`.
6. **Конфигурация:** Все параметры читаются из env. Если коллектор недоступен, сервис работает (телеметрия отключается).
7. **Отступления от предложенной структуры:**
   - Сгенерированный код лежит в `api/`, а не в `internal/generated/`, так как это стандартное расположение для `oapi-codegen` (разрешено `conventions.md`, п. 8).
   - Пакет `db` (пул `pgx`) лежит в `internal/db/`, а не в `internal/infra/postgres/`, так как он появился ещё в ЛР1, и его перенос потребовал бы масштабного рефакторинга без изменения функциональности.
8. **Экспортируемые интерфейсы вместо неэкспортируемых:** В задании предлагается делать интерфейсы неэкспортируемыми (`tripRepository`). Однако для генерации моков в пакете `_test` (как требует тот же пункт 4.1) через `mockgen` интерфейсы должны быть экспортируемыми, иначе `mockgen` не видит их из внешнего пакета. Поэтому сделала их экспортируемыми, но объявила на стороне потребителя (в `contract.go` юзкейсов).
9. **Логика работы с БД в репозитории:** Оставила всю SQL-логику (включая `INSERT` в две таблицы и проверку `RowsAffected` для `finish`) в репозитории, а не в юзкейсе. Юзкейс лишь оборачивает вызов репозитория в транзакцию (`txManager.Do`). Это позволяет не протекать SQL в бизнес-логику.
10. **Метрика db.client.operation.duration:** Реализована вручную в репозитории (через defer и замер времени). В качестве db.collection.name используется "trips" (упрощение для учебного проекта, так как в рамках одного метода Save пишем в две таблицы)
11. **Отключение автоматических метрик `otelhttp`:** Библиотека `otelhttp` по умолчанию создаёт свои HTTP-метрики, которые дублируют наши и не умеют определять маршруты `chi` (пишут `unknown`). Отключены через `WithMeterProvider(noop.NewMeterProvider())`, оставив только трейсы, а метрики сами в middleware.
